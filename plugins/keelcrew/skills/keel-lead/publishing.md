# Publishing the board

Publishing the board (an update, or keel-setup step 5). The board folder holds `index.html` (the page, with an import map), `capabilities.json`, and about 150 modules and a stylesheet, each named by its content (`lib-ui.<hash>.js`, `app.<hash>.css`); `manifest.json` lists every file with its hash. A changed module gets a new name, so a release only adds files, and the live page keeps loading its own files until the new `index.html` is up. The Artifact tool publishes only files the publishing session has read in full, so Haiku subagents read and publish them in batches; you never read the modules yourself.
1. Copy the folder into a new scratchpad folder `board-<version>` (`cp`), since the Artifact tool publishes only from there.
2. Read its `manifest.json`, and `crew/lead.boardFiles` (the manifest last published; none on a first setup). **New** is each file in the manifest whose hash differs from `boardFiles` (every file when there is none). **Old** is each name in `boardFiles` that the manifest lacks; with no `boardFiles` and an existing board, list its files yourself (Artifact `action: "list"`, `scope: "files"`, `url`) and Old is each listed name the manifest lacks. Nothing new and nothing old: skip to the `update` of `crew/lead` (keel-lead's update item; in keel-setup, its step 5 batch).
3. **Batches**, by size on disk (`ls -l`): the new files except `index.html` and `capabilities.json` go into batches of at most 200 KB each (about 3 for a whole board). Then one **last batch**: `index.html` (always), `capabilities.json` when new, and the Old names to remove. When the new files total 200 KB or less (most updates), there is just the last batch, holding them too: one subagent publishes everything. Earlier batches only add files the live page doesn't load yet, so they change nothing the captain sees, and the last batch switches the board over at once.
4. Run the batches in order, one at a time: the Agent tool with `subagent_type: "general-purpose"` and `model: "haiku"` (a small model is enough for this read-and-publish work), never `isolation`, and the prompt below, filled in for that batch. Wait for its result before the next: when the app runs it in the background, say in one chat line that the board update is underway and end the turn; its result wakes you, and you go on from there. If it replies PARTIAL, split that batch in two and run both; PARTIAL on a batch of one file, or a refusal, stops the run (keel-lead's update item says which card; in keel-setup, tell the captain). A batch is safe to resend.

The subagent's prompt (fill in the `<...>`; keep only the lines for this batch's case):
> Publish files to the Keelcrew board artifact `<board url, or "a new artifact">`. Use only the Artifact, Read and Skill tools, and change nothing else. If any read in these steps says it's partial or truncated, publish nothing and reply "PARTIAL <file>".
> 1. (every batch with a board URL, including later batches of a new board) Artifact `action: "read"` with `url: "<board url>"` and `path: "index.html"`: it saves the live page to a local file and says where. Read that file in full, once. Then Artifact `action: "list"`, `scope: "files"`, `url: "<board url>"`.
> 2. Read each of these files in full with the Read tool (`allow_large: true`), each once: <full paths of this batch's files>. (when this batch publishes the new page) Also Read `<scratch folder>/index.html` in full.
> 3. (capabilities.json in this batch) Load the artifact-capabilities skill with the Skill tool, then Read `<scratch folder>/capabilities.json`.
> 4. One Artifact publish with: `file_path`: `<scratch folder>/index.html` when this batch publishes the new page (the last batch, every batch of a new board), otherwise the file step 1 saved the live page to (so the page stays as it is); `url: "<board url>"` (any batch with a board URL); `icon: "board"` (only the first publish of a new board); `files`: `{"<name>": "<full path>", ...}` for this batch's files, plus `"<old name>": null` for each Old name (last batch only); `capabilities`: the contents of capabilities.json exactly as written (only when it's in this batch).
> 5. Reply with the publish result line (the URL and version), or the exact refusal.
