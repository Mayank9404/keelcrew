# Keelcrew architecture

Keelcrew is a crew of Claude Code sessions in the Claude desktop app. A **Mate** session takes in work (Jira tickets and anything the captain asks), staffs it with **agents** (engineer, QA, reviewer and more), and keeps the captain informed through the **Keelcrew board**, a private web page (a claude.ai artifact) with cards, chat and approvals. Outside writes through GitHub need the captain's approval (an engineer's own pushes and PRs aside), and a **policy hook** enforces that in every crew session. The browser is open: any crew member uses any web page. Connectors are open to every role but the read-only and drafts ones; Claude Code's own permissions and auto mode judge those calls.

Each person runs their own crew and their own board. A **team pack** holds everything specific to a team (repos, base branches, Jira, PR gate, extra rules); the core knows nothing about any one team.

This file is the contract every part is built to. Change it first, then the code.

Roles: `lead` (one per Mac), `engineer` (one per ticket: `keelctl register` refuses a session that worked another ticket, and a second worktree for a ticket whose first is still in the crew; a fresh session may take over the same worktree when the Mate re-staffs), `agent` (any other agent session, e.g. QA, with `agent: <id>`), `job` (a scheduled run; pruned after 24 h).

**Harbour light.** In the Mate's session the panel sets the Harbour light look (`settings/main.harbourLook`, on unless false; switching it off clears it). The look is a backdrop scene with frosted glass and no `colors`: the Claude app paints a theme's `colors` across every session, while a backdrop stays in the session that set it. A session has one theme and the latest set wins, so while the look is on the panel refuses another plugin's `theme.set` and `theme.clear` there (`otherLook`); the engine's own calls pass, and other sessions never set the look. Hooking `theme.*` needs an engine with `$.theme` (tested on Claude Code 2.1.326). It draws, in the Claude app, a harbour behind the chat from the crew's state each minute: a magenta pennant and beam while cards wait for the captain, today's watches (the schedules of the agents switched on), this week (crew tickets merged, QA first pass, new lessons), and the crew moored by state; above the prompt, a row with the same counts plus paused sessions and unread alerts. A ```` ```keelcrew ```` block (one JSON object: `crew`, `you`, `learned`, `deny` or `wake`) in a reply or a crew message is drawn as a card; a crew card's voyage track times each stage from `phases.json` (each ticket's phase changes, written by the panel); a needs-you card for a launch card answers it as `/keel-panel` does. The terminal shows each block as one line. No cost is shown.

**Alerts.** `alerts/<ts>-<kind>-<id>.json` `{kind: denials|budget|lost-session|..., key?, sessionId?, summary, at}`. The panel mod in the Mate session names new ones in its "Keelcrew board" wake (`alert <file>`); `keelctl alerts seen <id>` moves handled files to `alerts/seen/`.

Every decision read uses `readJsonStrict`: a damaged file throws `CorruptFileError` (so does a crew.json or config.json of the wrong shape), and the policy then **asks** for anything gated instead of allowing it. Display-only reads may use `readJsonLoose`. Locks (`withLock`) carry `{pid, token}`: a lock is taken over only when its holder's process is gone and released only by its holder; hooks wait at most 1.5 s and then refuse or ask.

## Rules

`rules/rules.json` holds the generic rules; the pack's `policy` adds `denyBash`, `protectedBranches`, `readOnlyServers`, `readTools`. `core/rules.mjs` `loadRules(pack)` merges and compiles them. Nobody else hardcodes a rule, a ship choice or the TTL. The board imports `rules.json` at build time for its "what the crew may do" text. The mod keeps its own copy of the ship choices (it can't import node modules); a test asserts they match. Its approvals go through `keelctl grant`, so the TTL is the helper's alone.

Ship choices: **Open PR** (push + PR), **Draft PR** (push + draft PR), **Push only** (push), **Not yet** (clears). An approval lasts the approval time in `rules.json` (`risk.ttlMinutes` for its tier, never longer than `ship.grantTtlMinutes`; 14 days at every tier) and records `head`, the commit approved; if the worktree's HEAD differs when the engineer pushes, the policy asks again.

**Risk tiers.** `rules.json` `risk`: `{patterns: {high: [{pattern, why}], medium: [...]}, size: {medium: 400, high: 1200}, ttlMinutes: {low: 20160, medium: 20160, high: 20160}}`; a pack adds patterns (the example pack: migrations, settings, auth and permission code, raw SQL files, deleted files). `core/risk.mjs` `assessRisk(dir, base)` → `{tier: low|medium|high, reasons[], files, added, deleted}` from `git diff --numstat` and the changed paths. `writeGrant` records `risk`; the approval time is the same at every tier (the captain's choice), so the tier changes what the card shows, not how long an approval lasts. The helper's read-only `risk {key}` returns it for the board; the engineer puts it on the launch card as `risk`.

**Approving from the phone.** Where the board can't reach the helper (a phone, a browser), an answer to a launch card or an "Approve and post" card is written to the card with `grantPending`, the answer's snapshot `{choice, at, key, head?, post?}` (the ticket, commit and post target the board showed), instead of reopening it (Settings → Shipping, `settings/main.phoneApprovals`, on by default). Within a minute the Mate's panel carries it out from the snapshot alone (never the card's other fields, which crew sessions may change; a snapshot it can't read fails) with `keelctl grant ship|post`, which calls the helper's own `approve` and `approve_post` (same head pinning, ancestry check, risk TTL, Not yet clearing; answers over `org.phoneGrantMaxAgeHours` old do nothing), records the outcome in `phone-grants.json` and wakes the Mate ("Phone answer: …"), which sets `grantPending: false` with `grantResult` or `grantError` (the board then opens the card to answer again). The panel's own `/keel-panel` click answers the card the same way (pinned to the version shown), then runs the same `keelctl grant ship`; a refused approval opens the card again, and on a card that names no full commit id only Not yet goes through. The policy refuses `keelctl grant` in any form (also under another name: the words `grant` then `ship` or `post`, or interpreter code that reaches the helper's approve code), and any board write that sets a card's `grantPending` to anything but false or null, from every crew session, the Mate's included; false or null only on a card whose answer `phone-grants.json` records, inbox writes only with inline data (never `file_path`), and deleting a card only from the Mate; the board's `db` rules let only the captain write `inbox`. The policy matches a push to an approval only when it runs on its own from the worktree (other ship steps and output filters such as `| tail` may sit beside it), with no `cd` or `-C`, to a named remote, sending `HEAD` or the checked-out branch; anything else needs a person. Rules read commands with git's own options removed (`git -C x push` is a push) and line continuations joined.

**Prompt mode.** Crew sessions run unattended, so a prompt there waits for nobody. With `config.promptMode` `deny` (the default) every policy answer that would ask a crew member is a denial naming the next step: a launch card for pushes and PRs, a draft card for outside writes (approved, it lets exactly one post through), else a message to the Mate (the Mate itself: a decision card). These denials count toward a pause only when the same call is refused `denials.softRetries` (3) times in a row, and then count for all three. `promptMode: ask` keeps the native prompt. When a crew file can't be read the policy asks either way.

**One-shot posts.** An approved draft card (writer, comms, release, reviewer comments) lets exactly one outside write through. `core/posts.mjs`: `writePostGrant({key, tool, match?, via, ttlMinutes = 30})` → `HOME/posts/<id>.json` `{id, key, tool (exact name or /regex/), match (text the tool input must contain), uses: 1, expires, via}`; `consumePostGrant(tool, input)` (under lock) returns and uses up a matching grant. Policy: a GitHub write, or a drafts role's connector write, with a live matching post grant is allowed and consumed. The helper's write tool `approve_post {key, tool, match?}` creates one (board button "Approve and post"); the panel can too, with the same file shape.

**Denial escalation.** The policy counts denials per session in `HOME/denials/<sessionId>.json` `{consecutive, total, reasons[], paused}`; any allowed call resets `consecutive`. At 5 in a row or 40 in total the session is paused: every tool except Read, Grep, Glob and messaging the Mate is denied with a reason, and an alert is written. `keelctl unpause <sessionId|KEY>` (Mate only) or a board request `{kind: "unpause", key}` clears it.

**What the policy covers.** Bash and any other built-in tool that carries a `command` (Monitor, PowerShell) are read as shell commands. File tools are checked by path (resolved from the session's folder, `~` expanded): secrets, the crew's own files, git's own `.git` files, and for engineers and agents anything outside their folder. Built-in tools not in `policy.localTools` need a person. Every `gh` command writes to GitHub unless it is a known read (`policy.githubWrite.reads`; `gh api` reads unless it has a write method, fields without `-X GET`, `--input`, or graphql), for every crew member, unless a one-shot post covers it; the terminal and the app's session controls always need a person. Outside connectors run freely for the Mate, engineers and agents, except a CI build (`policy.deployTools`: trigger, rebuild or replay, as a Jenkins connector names them), which needs a person; for a reader or drafts role a connector tool writes when any clause of its name (`get_or_create_x`) starts with a write verb. The helper's read tools run quietly; its board-only tools are denied to everyone.

**Agents that never ship.** A manifest's `canShip` (default: true for `kind: ticket`, false otherwise; every shipped agent but the engineer sets false) decides whether an agent or job may push or open a PR at all. When it may not, those are denied outright, approval or not.

## Core API (`plugins/keelcrew/core`)

- `paths.mjs`: `HOME`, `PLUGIN_ROOT`, `hash16(dir)`, `expand(p)`, `inside(root, p)`, `paths.*`.
- `fsx.mjs`: `readJsonStrict`, `readJsonLoose`, `writeJsonAtomic`, `withLock(lockPath, fn, {timeoutMs, staleMs})`, `appendRotating(path, line, maxBytes)`, `CorruptFileError`.
- `rules.mjs`: `loadRules(packName)`, `loadPack(name)`, `pushesProtected(cmd, branches)`.
- `install.mjs`: `linkAll(root)` (setup: `keelctl` and `keelcrew-helper` in ~/.keelcrew/bin), `healLinks(root)` (session start: re-points a missing or broken link, or one running an older version from Claude Code's plugin cache or its plugins synced from claude.ai, so a session still on the old version never pulls it back; a link to a checkout, and a file that isn't a link, are left alone), `installHelperEntry()` (adds only the `keelcrew-local` entry to the Claude app's config, through a symlink and keeping its mode; the first run keeps a `.keelcrew-backup` copy), `claudeAppRunning()`.
- `doctor.mjs`: `runDoctor({fix, safe})` (`safe`: only `SAFE_FIXES`, housekeeping with nothing to decide, and crew entries only for gone folders) → `{checks: [{id, label, status: 'ok'|'warn'|'fail', detail, fixed?}]}`, shared by `keelctl doctor` and the helper's `doctor` tool.
- `crew.mjs`: `readConfig`, `updateConfig(patch)`, `readRegistry`, `updateRegistry(fn)`, `memberFor(cwd, sessionId, reg?)`, `leadOf(reg?)`.
- `grants.mjs`: `readGrant(dir, key?, now?)`, `writeGrant({key, dir, choice, via, head?, packName?, now?})`, `clearGrant(dir)`.
- `memory.mjs`: `addLesson(l)`, `listLessons({scope?, includeRetired?})`, `forgetLesson(key)`, `pinLesson(key)`, `scopeLesson(key, {task?, repo?, agent?, area?})` (a `task` lesson reaches only that ticket's session and the Mate), `compilePlaybook()` → markdown, `playbookFor({role, repo?, agent?, task?})` → markdown. Lessons: `{id, at, type: preference|style|decision|correction|process|repo-fact, key, text, scope: {repo?, agent?, area? (a topic label: it filters `memory list --area`, never who gets a lesson)}, evidence: [{source: chat|card|pr-review|edit|commit|owner, ref, quote?}], confidence: 0..1, status: candidate|active|pinned|retired, supersedes?}`. `lessons.jsonl` is append-only; the newest line per `key` wins; `status: retired` forgets. Every change commits in the memory git repo.
- `agents.mjs`: `listAgents()` → manifests (validated), `agentById(id)`, `canShipOf(manifest)`, `memberCanShip(member)`.
- `policy.mjs`: `policyDecision(hookInput)` → `{decision: allow|ask|deny|null, reason}`; `hooks/policy.mjs` is a dependency-free entry that answers for crew members even when this module fails to load or throws.
- `githooks.mjs`: `installPushGuard(dir)`, `removePushGuard(dir)`, `pushGuardStatus(dir)`, `checkPush({dir, input})` (what `hooks/git-pre-push.mjs` runs).
- `membership.mjs`: `unregisterDir(dir)` (entry, sessions, approval, push check), `guardFolder(dir)`, `staleMembers()`, `pruneMembers()`.
- `costs.mjs`: `usageOf(transcript, since)`, `transcriptsOf(folder)`, `costs({key?})`: spend per crew folder (`key, agent, role, costUsd, tokens, since, transcripts`) across every transcript the folder has had (each session registered there, earlier ones the activity hook recorded, and their `subagents/*.jsonl`), per ticket and per role. The helper's read-only `costs` and `keelctl costs [--key K] [--json]` return the same numbers.

**Lesson lifecycle.** Lesson `status`: `candidate | active | pinned | retired`. New lessons are candidates unless the source is `owner` (said directly) or the captain approved them; adding the same key again appends evidence (an active or pinned lesson keeps its text, type, scope and confidence; only the Mate's `keelctl memory edit` rewords it); a candidate becomes active only when the Mate promotes it on the captain's OK. Only active and pinned lessons enter the standing orders. Candidates unseen for 30 days retire; active lessons unseen for 90 days are flagged stale. `keelctl memory promote <key>` and `keelctl memory diff` (changes to the standing orders since the last approved version, for the learner's approval card). Lesson types never include permissions: the learner cannot grant authority.

## Agents

An agent is `agents/<id>.json` + its skill. The Mate staffs only agents switched on in the board's Settings → Crew (`settings/main.agents[id].enabled`, default from the manifest). The manifest's fields (with an example), the unattended protocol every agent follows and the `KEEL_RESULT` line every run ends with are defined in [agents.md](agents.md), sections 1 and 4.

- Mate folder settings (`core/leadsettings.mjs`): Keelcrew owns `permissions.defaultMode` and `autoCompactWindow` in `<leadDir>/.claude/settings.local.json` (defaults in rules.json `sessions`; the captain's compact window is config.json `compactWindow`, set from board Settings through the helper's `config_set`). `keelctl doctor` checks them and `--fix` applies them; every other key in the file is the captain's.
- `runAs: session` starts a new Code session the way engineers start (`settings/main.sessions.startMethod`: `card`, the default, is a `start_session` proposal in the Mate session plus a board `start` card whose button opens the Mate session through the helper's `open_session` with key `lead`, where the captain clicks Start; `routine` is a run of a one-off scheduled task; briefs live in `~/.keelcrew/briefs/<id>.md`), registered with `keelctl register agent <KEY> --agent <id>`.
- `runAs: subagent` runs inside the Mate's or the engineer's own session with the Agent tool (cheap, no new session).
- `runAs: schedule` is a recurring scheduled task the Mate keeps in step with Settings.
- A pack's `agents[id]` adds team-specific skills and notes the agent's brief must include.

## The helper (`keelcrew-local`)

## The company

**Packaging.** `departments/<id>.json` `{id, name, summary, head, order, colour, budgetShare, defaultEnabled, switchable}` (ceo, engineering, product, marketing, support, operations). Role manifests add `department, reportsTo, memberKind (human|engineer|contractor|agent), policy (lead|code|agent|docs|reader|drafts), reads, drafts, outputs, metrics, cards, budgetShare, proposedModel`; a proposed model is only a suggestion in Settings → Crew, never used until the captain picks it. rules.json `org` holds seats, proactive and spend thresholds.

**Policy profiles.** `profileOf(member)`: the manifest's `policy`, else lead → lead, engineer → code, agent and job → agent, anything else → reader. `reader` writes nothing but its scratch notes (file tools and the shell: no file writes, interpreter code or git changes) and makes no connector write. `drafts` never sends (rules `policy.sendTools`) and its other connector writes need a post grant. Every other profile uses outside connectors freely. Browser tools are the same in every profile: any web page (http or https), clicks and typing included; only a page script that may send data, change the page or leave it, a file upload, or a preview started by name (a `launch.json` command) asks. A contractor is an engineer that ships only low-risk mechanical changes (its skill stops it otherwise); in card mode its draft PR skips the launch card only at low risk (an engineer's also at medium). Mate-only crew commands are read with the CLI's own argument parser (`core/cliargs.mjs`).

| File | Writer | What |

**Staffing.** Every ticket gets a fresh engineer. `keelctl org staff <KEY> --difficulty d [--mechanical]`: mechanical tickets go to a contractor when that role is on; with every seat taken the ticket waits. A seat is an engineer whose row is active (or that joined in the last day). The model is `modelFor`'s (see Models). The engineer gets its repo's lessons when it registers; guidance for one folder lives in that folder's `CLAUDE.md`.

**Proactive work.** The suggest agent scans the repos in its `repos` setting (empty: all) twice a weekday for security issues, production errors, slow endpoints, CI and test gaps, code health, dependency risk and old unassigned bugs, and posts ranked proposal cards tagged with their `source`. A source whose cards are rarely taken (hit rate under `proactiveMinHitRate` over the last `proactiveHitWindow`) pauses for `proactivePauseDays`, as the CTO and PM do. With `autoStart` on, `keelctl org proactive` says when the Mate may start a small, confident, non-security card by itself (within `autoStartPerDay` and `autoStartUsagePct` of the weekly bar, counted from tasks marked `autoStarted`); the launch card still waits for the captain.

**Models.** Every model and effort is set in one place, the board's Settings → Crew: `settings/main.org.models.approved` (`{model, effort}` per role id, `lead` and `subagents`; `{byDifficulty}` for the engineer), mirrored to `org.json`. **Board.** Settings → Crew (team and role switches, models, schedules), Settings → Tasks (goals), Settings → Limits (weekly shares), task rows with engineer or contractor, goal and spend flags, and held and ranked cards. The helper adds `org` (read); `crew_state` adds `merges`, `spend`.

## Security model

The policy layer exists so a crew of unattended sessions can't ship, post or break things by mistake, and so text an agent reads (a ticket, a web page, a PR comment) can't casually talk it into doing so. The browser is outside that guard: a crew member clicks, types and navigates on any web page, in the captain's signed-in Chrome too, so a page or a click can send data. It is a guardrail, not a sandbox.

**What it guarantees**
- Shipping has two modes (`config.shipMode`, the board's Settings switch; `rules.json` `ship.defaultMode` when unset). **free** (the default): an engineer pushes its checked-out commit to its own branch, opens PRs on its repo and edits, readies and comments on its own PR, at any risk, without a card; each such step is allowed when it runs as its own command in plain words (bare `git` or `gh`, no `$(…)`, backticks, variables, unquoted braces, backslashes or unquoted heredocs, and for `gh pr` only known flags), and chained with anything else it is left to Claude Code's own checks. A step that names another repo, branch or PR (`--repo`, `--head`, a variable, wrapper or path in front, `HEAD:other`, `--delete-branch`) still needs the card. **card**: an engineer pushes its own branch freely and, while `keelctl risk` says low or medium and the ticket has no PR yet (`prUrl` in `summary.json`), opens a draft PR; it also replies on its own PR (`gh pr comment`, review-thread replies); other PRs (non-draft, ready, edit, high risk) need the card. In both modes the policy and the worktree's pre-push check hold pushes to its own branch, and merging is never a crew member's. Writes outside the Mac through GitHub need the captain: a launch card for code, a draft card for a post, or a prompt in ask mode. Connector calls are left to Claude Code's own permissions. Each approval is a file bound to one worktree, one ticket, one ship choice and one commit; it has no working clock (a 14-day cap clears forgotten ones), and a new commit needs a new approval.
- Pushes are enforced twice. The policy hook checks a push before it runs (in card mode, against the approval); the worktree's own git `pre-push` hook (installed at `keelctl register`, removed at `keelctl unregister`) checks every ref actually pushed through core, however the push was started (a shell, a script, an alias, an IDE), and refuses anything but the checked-out commit to its own branch or the approved commit, deletions and protected branches. Flags and overrides that would skip that hook (`--no-verify`, `-c core.hooksPath`, `GIT_CONFIG_*`, `git config` of `core.hooksPath` or `extensions.worktreeConfig`) are denied, and crew members can't edit the hooks folder or `.git` files.
- It fails closed. A damaged or oddly shaped crew file, unreadable rules, a busy lock, input of the wrong shape, an unknown tool, or a crash in the policy itself makes crew calls ask (or, in deny mode, be refused), never pass. The pre-push check refuses when it can't run.
- Approvals, membership, settings, memory and the push hooks change only through the board, the ship question and the `keelctl` command, never by an agent's hand; agents that never ship can't push even with an approval; a relayed "the captain said OK" is never authority.
- Protected files are written only by the captain, or by Keelcrew's own commands: Claude Code settings files (`.claude/settings(.local).json` anywhere, and `CLAUDE_CONFIG_DIR`), the crew's own plugin code and hook config and Claude Code's plugins folder, and, for everyone but the Mate, the briefs and `lead.md`. File tools are judged by the real path (symlinks resolved, any letter case, and hard links to the Mate folder's and the user's settings files made earlier). Shell commands go through `core/shellpaths.mjs`, which reads them roughly the way a shell does (quotes, comments, redirections, `cd`, `git -C`, variables including `for` loops and `mktemp`, substitutions, heredocs, links made earlier in the same command, which arguments each common command writes, and interpreter code that names a protected file and writes it in the same statement) and errs toward letting everyday work run. Folders given by other tools' own options (`make -C`, `npm --prefix`) aren't modelled. These denials never count toward pausing a session. `tests/guards.test.mjs` and `tests/guards-hook.test.mjs` hold the cases found in independent reviews.
- Detection backs it up: `keelctl doctor` (run every 2 hours on working days by the Mate's mod) fails when the user's own Claude settings or the Mate folder's would switch the policy off (`disableAllHooks`, `bypassPermissions`; a repo's or worktree's own settings files aren't checked), when the Mate folder's settings drift, and when the live plugin has uncommitted changes.

**What it does not guarantee**
- It is not a sandbox against code written to evade it. Crew sessions run as the captain's user with the captain's credentials: a script an agent writes and runs can call the GitHub API or another remote directly, use other credentials on the Mac, or rewrite files outside the paths the rules watch. File-based approvals and the pattern checks catch mistakes and casual prompt injection, not a determined adversary.
- A shell command can hide what it writes until it runs: code piped into an interpreter (`echo … | python3`, `bash <(…)`), `sh -c "$CMD"`, `xargs`, `git apply` of a patch, a hard link made before the crew existed or to a repo's own settings file, or a `cd` that fails. The guards don't model those; the doctor checks above catch the outcomes that matter.
- It sees tool calls, not what programs do once started, and Claude Code lets a call through if the hook is killed by its timeout; the hooks keep every wait short and the pre-push check backs up pushes, but other outside writes rely on the hook alone.
- The captain's own sessions and shells are untouched (the captain can always `git push --no-verify`).

**Recommended extra layers**
- GitHub branch protection (or rulesets) on every base and release branch (`main`, `develop`, `release`): no direct pushes, no force pushes, no deletions, status checks required.
- Required pull request reviews (and CODEOWNERS where it matters), so nothing the crew pushes merges without a person.
- Least-privilege tokens: a fine-grained GitHub token for crew work limited to the repos it needs (contents and pull requests, no admin, no workflows or secrets), short-lived where possible; read-only database roles for agents; connectors scoped to what the crew uses.
- Keep `promptMode: deny` for unattended crews, and review `logs/policy.log` and the health agent's alerts.
